# Reading Validation

**Current implementation boundary — reviewed 2026-08-21.**

## 1. Purpose

Define how AquaLogic accepts, rejects, and evaluates incoming sensor
measurements. Device provenance and installed-sensor validation are implemented
under the Phase 01 domain foundation.

## 2. Validation layers

1. Device authentication
2. Fixed device-to-tank mapping
3. Payload/schema validation
4. Supported-parameter validation
5. Unit and range validation
6. Timestamp normalization
7. Decision-engine evaluation

## 3. Current contract

- Manual and device readings use the same installed-sensor bounds:
  temperature `-10..60`, pH `0..14`, turbidity `0..3000`, and TDS `0..5000`.
- Malformed, missing, non-finite, or out-of-range installed values are rejected;
  invalid input is never stored as a Normal reading.
- Device readings use the authenticated device's immutable tank mapping.
- `received_at` is generated by the server and cannot be client-controlled.
- Optional observation timestamps are normalized to UTC and retained for
  hardware-clock diagnostics and historical display.
- A late observation is accepted when its server receipt is valid. Operational
  freshness and latest-reading selection use `received_at`, not observation
  time.
- Duplicate suppression remains deferred because the hardware has no stable
  sample identifier.

Dissolved oxygen and ammonia remain nullable compatibility fields. No new bridge,
threshold, UI, notification, or workflow support is added for them in the
current release.

## 4. Core rule

An invalid reading must never be treated as a valid Normal reading. The shared
Phase 01 validation boundary is the authority for transport and persistence;
Phase 02 consumes only accepted readings.
